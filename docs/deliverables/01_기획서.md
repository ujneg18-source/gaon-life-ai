---

## 1. 한 줄 요약

> 서류 한 장을 읽는 OCR이 아니라, **청구 한 건**을 놓고 "서류가 다 왔는지 · 서로 맞는지 · 보상 대상인지"를 근거와 함께 짚어 주는 심사 담당자용 검토 도구.

---

## 2. 배경

### 2-1. 고객은 편해졌지만, 일은 보험사 안으로 옮겨 갔다
- 고객은 앱이나 메신저로 서류 사진을 보내면 끝난다. 그 사진을 읽고, 옮겨 적고, 약관과 맞춰 보는 일은 보험사 보상팀이 한다.
- 보험 서류는 OCR 중에서도 어려운 영역이다. 병원마다 양식이 다르고, 직인 · 손글씨 · 구김 · 촬영 왜곡이 섞인다. [1]

### 2-2. 단일 서류 인식은 이미 상용 수준이다
- 업스테이지 Document AI는 2023년 삼성생명 청구서류 7종에서 평균 95% 인식률을 냈고, 사람이 고쳐야 하는 항목은 약 4%였다. 수작업 대비 비용 · 시간을 최대 82% 줄였다고 밝혔다. [1]
- Upstage Studio 라이브러리에도 보험금 청구 서류의 분류 · 추출 워크플로가 이미 있다. [2]
- 따라서 남은 과제는 "한 장을 잘 읽기"가 아니라 **읽은 결과를 청구 단위로 엮어 판단 근거로 만드는 것**이다.

### 2-3. 전산 청구는 아직 과도기다
- 실손보험 청구 전산화(실손24)는 2024년 10월 병원급, 2025년 10월 의원 · 약국으로 확대됐다. [3]
- 2026년 9월 28일 기준 의료기관 연계율은 47.7%다(병원급 60.0%, 의원 · 약국 46.7%). [3]
- 실손24로 자동 전송되는 서류는 진료비 영수증 · 세부내역서 · 처방전 3종뿐이고, 진단서 · 조직검사 결과지 같은 서류는 여전히 사진으로 들어온다. [4]
- 보험사는 **정형 데이터와 비정형 이미지가 섞여 들어오는 청구**를 한동안 함께 처리해야 한다.

---

## 3. 문제 정의

| 문제 | 지금 | 결과 |
|---|---|---|
| 서류가 다 왔는지 | 청구 유형별 필수 서류를 담당자가 기억으로 확인 | 누락을 늦게 발견 → 보완 요청 지연 |
| 서류끼리 맞는지 | 진단일, 입원 기간 등을 서류마다 열어 대조 | 서류 수만큼 시간이 늘어남 |
| 보상 대상인지 | 영수증 항목을 약관 "보상하지 않는 사항"과 직접 대조 | 담당자 숙련도에 따라 결과가 달라짐 |
| 두 경로의 데이터 | 실손24 데이터와 사진 서류를 따로 확인 | 같은 항목도 형식이 달라 비교가 어려움 |

**그래서 필요한 것:** AI가 먼저 읽고, 사람이 봐야 할 것만 근거와 함께 올려 주는 도구.

---

## 4. 목표

1. 청구 1건의 서류를 **표준 스키마 하나로 정규화**한다 (실손24 데이터 + 사진 서류).
2. **누락 · 불일치 · 보상 제외 가능성**을 자동으로 찾고, 근거(서류 원본 위치, 약관 조항)를 붙인다.
3. 담당자는 **확인할 것만 확인**하고, 지급 판단은 사람이 한다.
4. Upstage 제품(Studio · Parse · Extract · Solar) 위에 고객사 맞춤 검토 레이어를 얹는 **도입 모델**을 보여준다.

## 5. 대상 사용자

| 사용자 | 하는 일 | 이 도구로 달라지는 점 |
|---|---|---|
| 심사 담당자 (고액 심사) | 진단금 · 수술비 · 입원일당 · 실손 청구 검토 | 서류를 하나씩 열지 않고, 이슈 목록부터 본다 |
| 운영 관리자 | 자동 처리 기준 · 서류 규칙 관리 | 신뢰도 기준과 규칙을 화면에서 바꾼다 |

---

## 6. 해결 방안

### 6-1. 3단계 검토
| 단계 | 질문 | 방법 | 예시 (시연) |
|---|---|---|---|
| 1. 누락 | 서류가 다 왔나? | 청구 유형별 필수 서류 규칙 | 세부내역서에 수술 기록이 있는데 수술확인서가 없음 |
| 2. 불일치 | 서류끼리 맞나? | 서류 간 교차검증 규칙 | 진단일이 조직검사 보고일보다 빠름, 입원 기간 1일 차이 |
| 3. 약관 대조 | 보상 대상인가? | 항목 분류 + 약관 RAG | 약제비 영수증의 영양제 항목 → 보상 제외 가능성 |

### 6-2. 주요 기능
- **워크스페이스:** 청구 검토함 → 청구건 상세(서류 확인 → 정보 대조 → 검토 결과 → 완료) → 문서 분석 · 검토(원본 뷰어, 원본 비교, 정규화 결과) → 보완 처리 → 검토 이력 → 운영 관리
- **업무 어시스턴트(챗봇):** "김유정 고객 서류 왔는지 확인하고 보완사항 검토해줘", "약제비 영수증에 보상 안 되는 거 있어?" 같은 질문에 청구 데이터와 약관을 근거로 답하고, 워크스페이스로 바로 이어 준다.
- **데모 로그인:** 심사 담당자 · 운영 관리자 두 역할. 역할에 따라 메뉴와 조회 범위가 다르고, 모든 조회는 이력에 남는다.

### 6-3. 시스템 구성
- Upstage Studio로 분류 · 추출 워크플로를 구성하고, 백엔드가 Agents API로 실행한다.
- 정규화 · 규칙 검사 · 약관 대조 · 라우팅은 자체 백엔드(FastAPI)에서 한다.
- 챗봇은 LangGraph로 질문 유형을 나누고, 약관 · 매뉴얼은 RAG(Qdrant + Solar Embedding)로 찾는다.
- 자세한 구조: `04_system_design.md`

## 7. 차별점

| 비교 대상 | 하는 일 | 이 PoC가 더하는 것 |
|---|---|---|
| 단일 서류 OCR 데모 | 서류 한 장의 값 추출 | 청구 단위 묶음, 서류 간 대조 |
| Studio "보험금 지급 심사 자동화 패키지" | 7종 분류 · 추출 | 조직검사 결과지 등 확장, 필수서류 · 교차검증 · 약관 대조, 검토 화면 |
| Studio "보험금 청구 문서 세트 자동 처리" | 분류 · 추출 · 일관성 요약 | 실손24 데이터 병합, 신뢰도 라우팅, 담당자 확인 흐름 · 이력, 성능 측정 |

핵심은 엔진을 새로 만드는 게 아니라, **검증된 엔진 위에 고객사 업무 흐름을 설계**한 것이다.

## 8. 데모 범위와 실제 도입 조건

이 PoC는 기능이 어떻게 동작하는지 보여주는 데모다. 실제 운영에는 아래가 필요하다.

| 영역 | 데모 | 실제 도입 |
|---|---|---|
| 약관 | 공개 표준약관 + 가상 특약 | 상품별 실제 약관, 개정 이력 |
| 사내 기준 | 가상 매뉴얼 | 보상 업무 매뉴얼, 심사 기준 |
| 법령 | 참고 수준 | 보험업법, 개인정보보호법, 의료법 검토 |
| 고객 · 계약 | 가상 고객 | 계약 · 특약 · 청구 이력 (기간계 연동) |
| 서류 | 가상 이미지, 실손24 모의 데이터 | 실제 청구 서류, 실손24 연계 |
| 의약품 정보 | 샘플 분류표 | 의약품 분류 데이터 |
| 보안 · 권한 | 데모 계정 2개 | 사내 계정 연동, 조회 통제, 사내 설치 |
| 판단 | AI는 근거 제시 | 지급 결정은 담당자 |

## 9. 기대 효과

수치는 PoC 평가로 측정한다. 아래는 측정할 항목이다.

| 효과 | 측정 지표 (`06_eval_plan.md`) |
|---|---|
| 확인할 것만 확인 | 전체 항목 중 담당자 확인으로 넘어간 비율 |
| 누락 · 불일치를 놓치지 않음 | 심어 둔 문제의 탐지율, 오탐률 |
| 근거 있는 답변 | 챗봇 근거 적중률, 근거 없을 때 거절 정확도 |
| 일관된 검토 | 같은 입력 → 같은 규칙 결과 |

참고: 업스테이지는 삼성생명 사례에서 수작업 대비 최대 82% 비용 · 시간 감축을 밝혔다. [1] 이 PoC의 수치는 가상 데이터 기준이므로 그대로 비교하지 않는다.

## 10. 평가 계획

- 가상 고객 8~10명, 청구 1~2건씩, 서류 4~8장. 정상 · 누락 · 불일치 · 저신뢰 · 보상 제외 항목을 골고루 심는다.
- 서류마다 정답 JSON을 만들어 항목 정확도와 탐지율을 잰다.
- 챗봇은 질문 30개 평가셋으로 근거 적중률과 답변 정확도를 잰다.
