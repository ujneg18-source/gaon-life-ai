# 02. 요구사항정의서

| 항목 | 내용 |
|---|---|
| 프로젝트 | 가온생명 AI — 보험금 지급 서류 검토 PoC |
| 버전 | v1.0 (2026-10-15) |
| 범위 | 기능 시연용 데모. 실제 도입 조건은 `01_scope.md` "데모 범위와 실제 도입 조건" 참고 |
| 우선순위 | M = 반드시 (시연에 필요) · S = 있으면 좋음 · C = 여유 있으면 |

## 1. 사용자와 역할

| 역할 | 설명 | 데모 계정 |
|---|---|---|
| 심사 담당자 (reviewer) | 고액 청구(진단금 · 수술비 · 입원일당 · 실손)를 검토하는 보상팀 담당자 | `reviewer@gaon.demo` (이름: 한지원) |
| 운영 관리자 (admin) | 자동 통과 기준과 서류 규칙을 관리하고 전체 청구를 보는 보상팀 관리자 | `admin@gaon.demo` (이름: 오세린) |

- 데모 계정 이름과 모든 고객 · 병원 정보는 가상이다.
- 로그인 화면에서 비밀번호 없이 "심사 담당자로 시작" / "관리자로 시작" 버튼으로 들어간다.

### 역할별 권한

| 기능 | 심사 담당자 | 운영 관리자 |
|---|---|---|
| 청구 검토함 | 나에게 배정된 청구만 | 전체 청구 |
| 청구건 상세 · 문서 분석 · 검토 | ○ (배정 건) | ○ (보기만, 확인 처리는 불가) |
| 보완 처리 | ○ | ○ |
| 검토 이력 | 배정 건 | 전체 |
| 운영 관리 | × (메뉴 숨김) | ○ |
| 업무 어시스턴트 (챗봇) | ○ | ○ |

## 2. 기능 요구사항

### 2-1. 공통 · 로그인

| ID | 요구사항 | 설명 | 우선 | 수용 기준 | 화면 |
|---|---|---|---|---|---|
| FR-01 | 데모 로그인 | 역할 버튼으로 로그인한다 | M | 버튼 클릭 시 해당 역할로 로그인되고, 상단에 이름 · 역할이 보인다 | SCR-01 |
| FR-02 | 역할별 권한 | 역할에 따라 메뉴와 조회 범위가 달라진다 | M | 담당자에게 운영 관리 메뉴가 보이지 않고, API도 403을 반환한다 | 전체 |
| FR-03 | 로그아웃 · 역할 전환 | 로그아웃 후 다른 역할로 다시 들어간다 | S | 로그아웃 시 로그인 화면으로 돌아간다 | SCR-01 |
| FR-04 | 메인 화면 | 업무 어시스턴트와 서류 검토 워크스페이스로 들어가는 입구 | M | 두 입구가 보이고 각각 해당 화면으로 이동한다 | SCR-02 |
| FR-05 | 통합 검색 | 고객 이름 · 청구번호 · 증권번호로 청구를 찾는다 | S | 일부만 입력해도 결과가 걸러진다 | SCR-10 |

### 2-2. 서류 처리 (백엔드 파이프라인)

| ID | 요구사항 | 설명 | 우선 | 수용 기준 | 화면 |
|---|---|---|---|---|---|
| FR-06 | 서류 업로드 | 한 청구에 이미지 · PDF 여러 장을 올린다 | M | 청구 1건에 최대 10장, jpg · png · pdf 허용 | SCR-11 |
| FR-07 | 실손24 데이터 수신 (모의) | 실손24로 받은 영수증 · 세부내역서 · 처방전 데이터를 청구에 연결한다 | M | 모의 JSON이 청구에 붙고 출처가 "실손24 데이터"로 표시된다 | SCR-11 |
| FR-08 | 서류 분류 | 올라온 파일이 어떤 서류인지 자동 분류한다 | M | Tier 1~3 서류 + 기타로 분류, 분류 신뢰도 함께 저장 | SCR-11 |
| FR-09 | 항목 추출 | Tier 1 · 2 서류에서 표준 스키마 항목을 뽑는다 | M | 항목마다 값 · 신뢰도 · 출처(Parse/OCR/데이터)가 저장된다 | SCR-12 |
| FR-10 | 정규화 · 형식 검증 | 날짜 · 질병코드(KCD) · 금액을 표준 형식으로 맞추고 검증한다 | M | 형식이 틀린 값은 "확인 필요" 이슈가 된다 | SCR-12 |
| FR-11 | 질병코드 정보 | 질병코드에 KCD 공식 명칭을 붙인다 | S | C18.7 → "구불결장의 악성 신생물" 표시 | SCR-12 |
| FR-12 | 처리 상태 표시 | 업로드 → 분류 → 추출 → 검증 진행 상태를 보여준다 | S | 처리 중 · 완료 · 실패가 구분되어 보인다 | SCR-10, 11 |

| FR-14 | 서류 간 교차검증 | 서류끼리 날짜 · 기간 · 코드가 맞는지 비교한다 | M | 시연 시나리오의 불일치 2건을 잡는다 | SCR-11, 12 |

| FR-16 | 신뢰도 라우팅 | 신뢰도가 기준보다 낮은 값은 담당자 확인으로 보낸다 | M | 기준값을 바꾸면 확인 필요 항목 수가 달라진다 | SCR-12, 15 |
| FR-17 | 청구 상태 자동 분류 | 검토 결과로 청구 상태를 자동 통과 / 검토 필요 / 보완 요청으로 나눈다 | M | 이슈가 없으면 자동 통과, 누락이 있으면 보완 요청 | SCR-10 |

## 3. 비기능 요구사항

| ID | 분류 | 요구사항 |
|---|---|---|
| NFR-01 | 개인정보 | 가상 데이터만 사용한다. 실존 인물 · 기관 정보, 실제 주민번호 · 계좌번호 형식을 쓰지 않는다 |
| NFR-02 | 보안 | API 키는 `.env`에서만 읽고 저장소에 커밋하지 않는다 |
| NFR-03 | 마스킹 | 신분증 · 통장 사본의 번호는 화면과 응답에서 가린다 |
| NFR-04 | 판단 경계 | AI는 근거 제시까지만 한다. 지급 여부 결정 문구를 만들지 않는다 |
| NFR-05 | 추적성 | 모든 조회 · 수정 · 확인은 검토 이력에 남는다 |
| NFR-06 | 설정 | 상수 · 경로 · 모델명 · 임계값은 `config.py` 한 곳에서 관리한다 |
| NFR-07 | 성능 | 시연 청구 1건(서류 6장)의 처리가 2분 안에 끝난다 (외부 API 응답 시간 포함 목표) |
| NFR-08 | 재현성 | 같은 서류 · 같은 설정이면 규칙 검사 결과가 같다 |
| NFR-09 | 사용성 | 처음 보는 사람도 설명 없이 검토 흐름을 따라갈 수 있다 (상태는 색 + 아이콘 + 글자) |
| NFR-10 | 반응형 | 1280px 이상 데스크톱 기준, 화면이 잘리지 않는다 |
